# Upstream parity ledger

This is a review ledger, not a merge queue. Upstream commits are evaluated
against this fork's dedicated-Chrome, exact-session recovery, Batch Oracle,
fail-closed dispatch, source-only distribution, and MIT-attribution contracts.
`pending` means the change has not been accepted or rejected; it is not a claim
that current fork behavior is equivalent.

The four classifications are:

- `adopted` — the change is present in this source candidate;
- `independently implemented` — local code and tests establish the relevant
  contract without importing the upstream commit;
- `not applicable` — the change belongs to authority or behavior deliberately
  absent from this fork;
- `pending` — a separate compatibility, product, or dependency review remains.

## Latest attachment and single-send review

The latest upstream change was reviewed as two related mechanisms:

1. **Attachment evidence.** Upstream adds per-file composer evidence so a
   filename-less preview can still prove which upload reached the composer. The
   current fork has no equivalent `attachmentEvidence` module or fixture set.
   This part remains `pending` and must not be inferred from remote basename
   staging.
2. **Single-send stability.** Upstream stabilizes click coordinates after
   activation and scroll, then performs one send attempt, treating an ambiguous
   commit timeout as non-retryable. The fork independently verifies the exact
   normalized prompt, baseline turns, owned target, and newly observed user
   turn before writing its commit receipt. It permits only a tightly gated
   retained-draft retry when evidence shows the first click did not commit.
   See [`src/browser/actions/promptComposer.ts`](../src/browser/actions/promptComposer.ts),
   [`src/browser/index.ts`](../src/browser/index.ts),
   [`tests/browser/promptComposer.test.ts`](../tests/browser/promptComposer.test.ts),
   and [`tests/browser/index.test.ts`](../tests/browser/index.test.ts).

Those contracts overlap in their goal—avoid duplicate sends—but are not
patch-equivalent. A blind merge would replace fork-specific recovery semantics
and is therefore rejected. Future adoption must combine attachment evidence
with the fork's exact-session receipt model and pass a real Chromium send-fault
proof before classification changes.
